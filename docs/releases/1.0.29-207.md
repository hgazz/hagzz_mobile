# Customer app 1.0.29+207 — identifier-free analytics and resilient startup

This release makes the advertising opt-out explicit at every configured layer and enforces a stricter identifier-free artifact policy. It cannot change previously uploaded binaries or the Play Console declaration.

## Advertising policy

The inspected 206 AAB did not contain `com.google.android.gms.permission.AD_ID`, but Firebase's merged manifest still supplied `ACCESS_ADSERVICES_AD_ID` and `ACCESS_ADSERVICES_ATTRIBUTION`. Its default ad storage/user-data flags were also unspecified. The dependency report traces `play-services-ads-identifier` to Firebase Analytics; a library's presence alone is not proof that an identifier was collected.

207 removes the traditional advertising-ID permission and the AdServices ID, attribution, and topics permissions from the merged manifest. Advertising-ID collection, advertising storage, ad user data, and ad personalization default to false. The Analytics service also explicitly denies the three advertising consent categories before enabling product event logging. It preserves existing analytics-storage consent rather than granting it automatically. Product analytics and Crashlytics remain; this is not a declaration that the app collects no data.

`verifyReleaseAdvertisingPolicy` checks the AGP merged manifest and is a dependency of release APK/AAB packaging. It fails on these advertising permissions, missing opt-out flags, or target SDK below 36. The task was tested against the old configuration and correctly failed, then passed after the manifest changes. `scripts/verify_android_release.py` independently checks the actual signed AAB; the old 206 AAB correctly fails the new advertising policy.

These are deliberately stricter project checks. Rejecting 206 under the new checks does not prove that it collected advertising IDs, that Play forced the declaration to Yes, or that advertising configuration caused the reviewer’s unresponsive-app report.

## Startup reliability

Only localization and local storage/session prerequisites delay navigation. Dart-side Firebase, Analytics, Crashlytics setup, and notification registration start after the application frame. A hung or failed optional initializer cannot replace the usable app with a startup error screen. Optional startup is scheduled once, even after local initialization recovery. Analytics event calls are safe before Firebase is ready and contain SDK failures/timeouts.

This retains 205/206 fixes for the unbounded notification-token wait found in 204, first-frame layout, serialized initialization retries, and loading feedback. It does not reproduce the reviewer's Android ANR or establish its complete cause. Native Android initialization, the Play-installed/protected build, actual device navigation, production API access, authentication, and booking/payment flows still need device testing.

## Build and artifact checks

With Flutter 3.35.7, JDK 17, Android SDK 36, the existing signing configuration, and resolved dependencies:

```sh
flutter pub get
flutter test
flutter build appbundle --release
```

For this environment's blocked Crashlytics upload endpoint only:

```sh
ORG_GRADLE_PROJECT_crashlyticsMappingUploadEnabled=false flutter build appbundle --release
```

Independent checks require Python 3.11+, a JDK, and bundletool:

```sh
python3 scripts/verify_android_release.py \
  --bundle build/app/outputs/bundle/release/app-release.aab \
  --bundletool /path/to/bundletool.jar \
  --version-code 207 --version-name 1.0.29 \
  --previous-bundle docs/releases/Hagzz-Customer-1.0.28-206.aab \
  --output verification.json
```

The signed AAB, verification report, and checksum are in this directory. The R8 mapping and resolved dependency lock are retained under `/workspace/artifacts/`.

The verifier checks identity/version, SDKs, advertising permissions/default flags, ABI coverage, 16 KB ELF64 load-segment alignment, bundle structure, JAR signature, unchanged signing certificate, and SHA-256. It does not certify device behavior or Google Play acceptance.

Retained 40 may still be the binary served to devices that cannot install 207 (API 21–23 or x86). Inspection of its source at `c10533a` confirms `FirebaseMessaging.instance.getToken()` is awaited without a timeout before `runApp`, the same concrete failure path found in 204. The published 40 binary/device behavior was not independently inspected. Uploading 207 does not update that code path. A release cannot be described as uniformly fixed while an older, differently configured binary remains distributed to that cohort. This is another reason to inspect the delivered version during Play-installed tests, not just the version uploaded in Console.
